## Challenge Objective

> `[SOURCE FACT]` Build a **working proof of concept** using AI software development tools.  
> `[SOURCE FACT]` Projects are **NOT** expected to be production-ready software.

**Theme:** *"Information you can trust"* `[SOURCE FACT]`

**Three challenge tracks:** `[SOURCE FACT]`

| # | Track |
|---|-------|
| 1 | Stability & Social Cohesion |
| 2 | Transparency & Accountability |
| 3 | Safety, Reporting & Protection |

- `[SOURCE FACT]` Cross-track entries are welcome — a single project may address more than one track.
- `[PROJECT IMPLICATION]` Ubuntu Ledger's **primary track** is **Transparency & Accountability**. Elements addressing Stability & Social Cohesion (e.g., civic trust in government data) may be surfaced as secondary track contributions.

## Judging Criteria

> `[SOURCE FACT]` Four criteria, **equally weighted** (no numeric scores were published).

| Criterion | Description | Source |
|-----------|-------------|--------|
| **Uniqueness** | How novel and unique the approach was to solving the problem | `[SOURCE FACT]` |
| **Scalability** | How well it can be scaled across geographies | `[SOURCE FACT]` |
| **AI Coding Usage** | How well AI coding tools were used to build the project | `[SOURCE FACT]` |
| **Presentation** | How well the submission is presented and aligned to the tracks | `[SOURCE FACT]` |

> `[INTERPRETATION]` "Equally weighted" suggests each criterion carries ~25% of the total score, but exact numeric weights were **not published** and should not be stated as fact.

**Judges' operating constraints** — factors judges will use to evaluate real-world fitness: `[SOURCE FACT]`

| Constraint | Description |
|------------|-------------|
| Trust & verification | Information must be accurate, traceable to credible sources, easy to verify |
| Low bandwidth & limited access | Solutions should remain useful with unreliable internet, limited mobile data, and basic devices |
| Accessibility & inclusion | Must serve users across different literacy levels, disabilities, and digital confidence levels |
| Privacy & security | Must protect user identity and data |
| Multilingual access | Arabic, French, Portuguese, and numerous local languages |
| Local relevance | Laws, institutions, and services vary by location |
| Clear next steps | Help users understand what they can do next |

## Submission Requirements

> `[SOURCE FACT]` Four required deliverables:

### 1. GitHub Repository
- `[SOURCE FACT]` Must be **public**
- `[SOURCE FACT]` Must include a **clear README** explaining what the project does and how to run it

### 2. Demo Video
- `[SOURCE FACT]` Accepted formats: **mp4, mov, webm, avi**
- `[SOURCE FACT]` Maximum file size: **250 MB**

### 3. Pitch Deck
- `[SOURCE FACT]` Format: **PDF only**
- `[SOURCE FACT]` Maximum file size: **100 MB**
- `[SOURCE FACT]` Must cover: **problem, users, solution, potential impact**

### 4. Written Summary
Must explain: `[SOURCE FACT]`
- Which track the submission belongs to
- What information sources were used
- The approach to trust and accuracy
- How AI coding tools were used

## Demo / Presentation Expectations

- `[SOURCE FACT]` The **Presentation** judging criterion explicitly evaluates how well the submission is presented and aligned to the tracks.
- `[INTERPRETATION]` The demo video is the primary vehicle for showing the working proof of concept; it should demonstrate real functionality, not slides alone.
- `[PROJECT IMPLICATION]` Ubuntu Ledger's demo should show: a working search or query flow, a verifiable source citation, and at least one low-bandwidth or offline scenario to address the access constraint.

---

## Technical Requirements

- `[SOURCE FACT]` The project must be a **working proof of concept** — it must function.
- `[SOURCE FACT]` Projects are explicitly **not** required to be production-ready.
- `[SOURCE FACT]` **AI coding tools** must have been used in development (evaluated as a judging criterion).
- `[INTERPRETATION]` The repository README must be sufficient for a judge to understand how to run the project — installation steps and a quick-start guide are strongly implied.
- `[PROJECT IMPLICATION]` Ubuntu Ledger must demonstrate AI-tool usage visibly (e.g., commit history, screenshots, or written summary describing which AI tools were used and how).

## Design / UX Expectations

> No explicit UX requirements were stated on the brief page. The following are interpretations from the operating constraints.

- `[INTERPRETATION]` Accessibility and inclusion constraint implies the UI/UX must be usable across literacy levels and disability profiles.
- `[INTERPRETATION]` Low-bandwidth constraint implies the interface should degrade gracefully or provide an offline/low-data mode.
- `[INTERPRETATION]` Multilingual access constraint implies at minimum English support with a documented path to language expansion; full multilingual support is aspirational.
- `[PROJECT IMPLICATION]` Ubuntu Ledger should document accessibility and low-bandwidth design decisions in the pitch deck and written summary.

- `[SOURCE FACT]` Demo video must be one of: mp4, mov, webm, or avi.
- `[SOURCE FACT]` Demo video is capped at **250 MB**.
- `[SOURCE FACT]` Pitch deck is capped at **100 MB**.
- `[INTERPRETATION]` The GitHub repository must remain public through the judging period to allow judge access.

## What This Means For Ubuntu Ledger

| Judging Criterion | Ubuntu Ledger Response |
|-------------------|------------------------|
| **Uniqueness** | Blockchain-anchored public-record ledger with AI-powered retrieval is a novel approach to civic transparency in the Kenyan context `[INTERPRETATION]` |
| **Scalability** | Architecture should be presented as replicable across counties and countries; highlight data-agnostic design `[PROJECT IMPLICATION]` |
| **AI Coding Usage** | Document every AI tool used (code generation, testing, design); include in written summary `[PROJECT IMPLICATION]` |
| **Presentation** | Pitch deck must explicitly map Ubuntu Ledger to Transparency & Accountability track; demo video must show real functionality `[PROJECT IMPLICATION]` |

**Operating constraints Ubuntu Ledger must address in deliverables:**

- `[PROJECT IMPLICATION]` **Trust & verification** — Show how ledger entries are sourced and verified; display provenance on every record.
- `[PROJECT IMPLICATION]` **Low bandwidth** — Demonstrate or describe a lightweight query path; note offline capability if available.
- `[PROJECT IMPLICATION]` **Accessibility** — Note plain-language summaries and any screen-reader or low-literacy considerations.
- `[PROJECT IMPLICATION]` **Privacy & security** — Describe how citizen identity is protected when accessing sensitive records.
- `[PROJECT IMPLICATION]` **Multilingual** — Acknowledge the constraint; document planned language support path.
- `[PROJECT IMPLICATION]` **Local relevance** — Ground examples in Kenyan laws, institutions, and county-level data.
- `[PROJECT IMPLICATION]` **Clear next steps** — Every query result should tell the user what they can do with the information.
